## Modelo y operaciones

`cards` representa identidad jugable; `card_printings` representa impresión/set/idioma/variante/tratamiento; `products`/`product_contents` representa pertenencia al producto, sin crear un set Proving Grounds ficticio. IDs UUID, números impresos conservados, claves numéricas derivadas, fuentes/versiones/checksum y campos desconocidos nullable. Sets adicionales deben recibir una secuencia explícita revisada; la BD exige OGN antes de SFD cuando ambos existen.

`catalog_printings` calcula elegibilidad mediante la política de rareza/tratamiento y la excepción de producto verificada. Una composición oficial Proving Grounds para una identidad/set/idioma tiene precedencia sobre la edición general, sin multiplicar filas por pertenecer a varios productos. La cantidad publicada del producto no interviene en el masterset. `collection_category` clasifica explícitamente el objetivo del usuario: Normal=3, Legend/Battlefield=1, desconocido=NULL; no deriva clasificaciones de datos incompletos.

Las tablas personales tienen RLS por `auth.uid()`. FKs compuestas mantienen propietario entre deck, línea, entrada y asignación. No se otorga DML directo a `anon`/`authenticated`; las escrituras de inventario y mazos pasan por `mutate_inventory(action, payload)`, que devuelve el ID afectado (puede ser NULL al liberar una asignación). No acepta `user_id` como autorización. Función `SECURITY DEFINER`, `search_path` vacío, objetos cualificados, ejecución sólo autenticada; funciones auxiliares en esquema privado sin acceso API.

| action | payload |
| --- | --- |
| `set_owned` | `printing_id`, `quantity` entero >=0 |
| `create_deck` | `name`, opcional `mode` (`theorycraft` por defecto), `format` descriptivo |
| `set_line` | `deck_id`, `card_id`, `section` descriptiva, `quantity` entero >=0; cero retira línea sin reservas |
| `allocate` | `deck_card_id`, `collection_entry_id`, `quantity` entero >=0; cero libera esa asignación |
| `set_mode` | `deck_id`, `mode`; theorycraft libera todas las reservas en la misma transacción |
| `delete_deck` | `deck_id`; cascada libera líneas/asignaciones |
| `duplicate_deck` | `deck_id`, opcional `name`; copia theorycraft sin asignaciones |

RPC valida sesión, dueño, elegibilidad, identidad compatible, modo físico, disponibilidad y cantidad requerida. Usa un advisory lock transaccional por propietario para **todas** estas operaciones, con lecturas posteriores al lock; sólo admite aislamiento READ COMMITTED para evitar snapshots previos al lock. Colisiones del hash sólo serializan propietarios adicionales. No hay reservas en theorycraft. Reducir owned por debajo de reserved falla y devuelve en `detail` los mazos afectados. Reducir una línea reservada exige liberar primero; la copia o conversión no fabrica inventario.

Restricciones enteras, checks, FKs y triggers diferidos aportan defensa adicional en la BD. `inventory_status` deriva reserved/available de asignaciones, sin descontarlas de owned ni de masterset. Las vistas usan `security_invoker` y no saltan RLS.

Secciones/formato son etiquetas descriptivas: no se fijan tamaños, dominios ni límites legales inventados. No existe perfil oficial validado en P0 y la BD sólo admite `Unverified`. Hasta resolver equivalencia de impresiones/idioma, una línea física sólo acepta una impresión exacta a la vez; hay que liberarla antes de cambiarla. Esta restricción conservadora de asignación no se presenta como regla del juego.

**Mantenimiento privilegiado:** no usar service-role ni SQL directo para modificar inventario saltando el RPC. Si una reparación necesita SQL privilegiado, debe mantener ownership, obtener el mismo lock por propietario y respetar todos los invariantes. Importaciones administrativas deben coordinar la publicación con escrituras personales (bloqueos de tablas en orden fijo o ventana de mantenimiento). El guard de catálogo rechaza cambios que vuelvan inelegible inventario existente; no remapea ni elimina cartas propias en silencio. El importador real aún no existe.

## Verificaciones ejecutadas

- Tipos (`npm run typecheck`) y ESLint (`npm run lint`): correctos.
- Dominio (`npm test`): 4 casos correctos; progreso por copias/cap/exceso/categorías pendientes, cantidades/disponibilidad, orden natural/números ausentes/desempate y política de imágenes.
- PostgreSQL 17 local desechable (`npm run test:db`): suite más 8 casos, correctos. Dos usuarios, permisos directos negados, RLS en tablas/vistas, enteros, tratamientos/variantes, excepción ficticia Proving Grounds, guard de catálogo, secuencia OGN/SFD, identidad, over-allocation, reducciones, READ COMMITTED, cambios de modo/copia/eliminación. Carrera real: conexión A reserva 2 de 3 y mantiene transacción abierta; B intenta reservar otras 2; se observa B esperando advisory lock; A confirma y B rechaza la operación sin exceder owned.
- Build Next.js (`npm run build`): correcto; rutas `/` y `/settings`, proxy SSR.
- Chromium (`npm run test:ui`): 2 casos correctos, viewport desktop 1440 y mobile 390; estado sin configuración, English, placeholder, foco inicial, navegación y ausencia de overflow del documento. Capturas revisadas visualmente.
- Auditoría de dependencias de producción (`npm audit --omit=dev --audit-level=high`): 0 vulnerabilidades reportadas.

La primera ejecución detectó y permitió corregir una ambigüedad PL/pgSQL y enlaces internos que incumplían lint. Las restricciones del sandbox también bloquearon npm, Docker/procesos de build e IPC del runner: se ejecutaron operaciones locales con revisión automática de permisos; el runner de dominio se cambió a `node --import tsx` sin servidor IPC de CLI. No se ocultaron estos fallos ni se contaron como éxitos.

**No ejecutado:** stack Supabase completo, Auth con cuenta/confirmación real, generación de tipos desde Supabase local, Storage, importación autorizada, comparación de checklist Riot, E2E de mutaciones desde UI, RAG/legalidad y backup/restore de un servicio alojado. La BD de prueba usa funciones Auth controladas; no sustituye las integraciones reales. No hubo llamadas a producción, despliegue, push, merge ni commit.
