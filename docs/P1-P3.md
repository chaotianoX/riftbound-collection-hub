# P1/P2/P3 — Prueba local de módulos

El blueprint v3.1 y AGENTS se conservan sin cambios. Esta entrega continúa P0 con la versión original autenticada por Supabase; no recupera historial ni inventa reglas Riot. Se prepara para publicación en una rama de GitHub y PR en borrador, sin merge ni despliegue. El modo demo sin cuenta queda excluido.

## Qué puedes probar

- **P1 / Collection:** catálogo elegible, búsqueda por nombre/CARD #, filtros set/tipo/dominio/rareza/propiedad/checklist de producto; grid/list con orden compartido, dirección y reset; todas las opciones del blueprint; preferencias de orden guardadas por cuenta. Ordena el conjunto completo antes de paginar. Cantidades enteras mediante servidor/RPC, con éxito sólo confirmado por BD, estado pending, error y detalles de mazos afectados. Detalle de impresión, procedencia, texto impreso y owned/reserved/available/objetivo/faltantes/excesos, más placeholder de imágenes.
- **P1 / Masterset:** progreso por copias y set, faltantes/excesos, resumen por tipo, filtro de incompletos y categorías pendientes visibles. Reservar no reduce propiedad/progreso. Los objetivos confirmados siguen siendo 3 Normal y 1 Legend/Battlefield; categorías sin decisión tienen objetivo NULL y progreso global indefinido.
- **P2 / Wishlist:** entradas manuales editables con objetivo total, prioridad y nota; razones Masterset y Deck añadidas explícitamente y deduplicadas por impresión. Las sugerencias viven en un panel independiente. Recalcula deficits sin sobrescribir intenciones manuales, fabricar owned ni insertar automáticamente sugerencias.
- **P2 / Dashboard:** owned, identidades distintas, faltantes, reservas, wishlist y progreso por set; métricas enlazadas; mazos físicos con déficit y legalidad separados. Estado honesto de fuentes, retrieval frente a sync y reglas aún no configuradas.
- **P3 / Decks:** crear/renombrar/eliminar/duplicar; buscar identidades y editar líneas por sección; theorycraft sin propiedad requerida ni reservas; elección explícita de impresión; cambio a physical, asignación a inventario real, conflictos y release transaccional; conversión a theorycraft libera todo; duplicación theorycraft sin reservas. Import/export textual con previsualización/resolución de IDs y creación atómica sin tocar colección.

**Dependencias oficiales pendientes:** dataset y derechos de cartas/imágenes; checklist completo y versiones reales de Proving Grounds; formato/perfil oficial de reglas/erratas/idioma/equivalencias. La legalidad se mantiene `Unverified`, sin declarar `Valid` o `Ready`. La parte de P3 de validación positiva/versionado de perfiles no está completa sin esa evidencia. Rules Assistant/ingesta/RAG son P4 y no están implementados.

## Semántica de adquisiciones

Los números guardados son **objetivos totales de propiedad**, no cantidades de compra pendientes:

```text
manual_goal = intención manual guardada (si existe)
masterset_goal = objetivo confirmado de la impresión (si se guarda esa razón)
physical_goal = suma de cantidades requeridas en mazos physical simultáneos,
                sólo cuando la impresión fue elegida explícitamente
acquisition_goal = max(manual_goal, masterset_goal, physical_goal)
remaining = max(acquisition_goal - owned, 0)
```

Mostrar cada razón, evitar sumar un objetivo de colección a las mismas copias ya requeridas por mazos y descontar inventario sólo una vez. Theorycraft muestra faltantes hipotéticos en su pantalla; no compite con reservas ni entra en demanda física simultánea. Una línea sin impresión elegida muestra pendiente, sin asumir equivalencias de idioma/set. Cambiar manual a cero retira sólo la razón manual; se pueden retirar razones derivadas o toda la entrada.

## Esquema, seguridad y evolución

- `202610080001_foundation.sql` permanece intacta.
- `202610080002_workspace.sql` añade bandera de fixture, wishlist, impresión preferida, RPC `mutate_workspace`, guards de integridad y snapshot consistente.
- `mutate_workspace` valida usuario por `auth.uid()`, usa el mismo advisory lock por dueño y delega operaciones de inventario a P0. Las tablas personales siguen sin DML directo para clientes. RLS y FKs compuestas protegen ownership. Triggers diferidos evitan eludir impresión elegida mediante el RPC anterior. Las importaciones fallan completas ante cualquier línea inválida o repetida.
- `workspace_snapshot` es security-invoker y usa una sola sentencia SQL para leer catálogo e información privada consistente; agrega arrays dentro de un valor JSON para evitar truncamiento por límite de 1000 filas de PostgREST. No tiene cache compartida por usuario.
- El orden y métricas derivan del mismo snapshot y funciones de dominio; no se escriben contadores desincronizados. Este enfoque carga el catálogo completo y es adecuado para el alcance inicial; un catálogo mucho mayor requerirá índices/paginación SQL equivalentes antes de ampliar el alcance.
- Sign-in/sign-out invalidan el layout para evitar reutilizar vistas privadas de otra sesión. Navegación entre módulos espera la confirmación/refresh de mutaciones pendientes.
- Imágenes se muestran sólo con derechos/ready/checksum y URL HTTPS revisada; no hay assets oficiales inventados ni base64. Ingesta/Storage real continúan pendientes.

Para actualizar una instalación P0 local, conservar sus datos:

```sh
npx --no-install supabase migration up --local
```

No reemplazar migraciones ya aplicadas, usar `db reset` en datos que deban conservarse o ejecutar el seed contra un proyecto real. Una recuperación con datos persistentes requiere backup/migración correctiva; producción no se tocó.

## Catálogo de prueba opcional

```sh
npm run fixtures:local -- --test-only
```

Sólo conecta a `127.0.0.1:54322`, contraseña local estándar del CLI, sin opción de URL remota. Rechaza mezclar fuentes autorizadas con fixtures y sólo registra datos sintéticos idempotentes de catálogo. No crea usuarios ni owned/reservas de ejemplo. Contiene OGN/SFD **para ejercitar la secuencia**, 64 cartas ficticias, una categoría pendiente y una variante excluida. El producto `TEST ONLY simulated Proving Grounds` es un escenario de software, **no el checklist Riot**. No trae imágenes oficiales, clasificaciones reales ni límites legales. La UI muestra siempre el banner TEST ONLY.

Si ya tienes un catálogo autorizado o configuración local distinta, usar un proyecto de pruebas separado; no modificar el script para apuntarlo a producción. El dueño deberá proveer la URL/nombre de dataset y condiciones de uso para reemplazar los fixtures por una importación autorizada.

## Formato de listas de mazo

`TSV v1`: una línea por identidad/ sección; campos separados por tabulación:

```text
quantity<TAB>section<TAB>card_uuid<TAB>printing_uuid_optional
```

`#` inicia comentario; conservar UUIDs canónicos, evitando nombres ambiguos. Cantidades positivas enteras, sección de 1–80 caracteres, hasta 500 líneas y 100.000 caracteres. Sin tabs/newlines en etiquetas de sección. Repetir identidad/sección es un error explícito; combinar cantidades antes de importar. La impresión opcional debe corresponder a la identidad y ser elegible. Preview muestra nombres resueltos y errores. Import siempre crea un nuevo theorycraft; no reemplaza un mazo existente ni registra cantidades en colección. Export llena el área de texto para copiar/guardar la lista.

## Servicios y verificaciones

`npm run test:db`: PostgreSQL 17 desechable, restricciones/RLS/transacciones/concurrencia entre conexiones, wishlist/preferencias/import/snapshot/propietarios. Su Auth stub es controlado y no se presenta como integración completa.

`npm run test:local`: harness desechable con **GoTrue, PostgREST y PostgreSQL reales**; gateway mínimo sólo loopback reemplaza Kong. Genera credenciales efímeras internamente, crea/borra exclusivamente sus contenedores/red, aplica migraciones y fixtures TEST ONLY, compila y ejecuta Playwright en desktop/móvil. No acepta URL remota ni usa secretos del usuario. Las confirmaciones de correo están deshabilitadas exclusivamente en este harness, para pruebas; no cambia el config de tu Supabase. Requiere Docker, imágenes de servicio y Chromium (ruta mediante `P0_CHROMIUM_PATH`). Es una prueba real de Auth/RPC/persistencia/RLS, **no** una validación de Supabase CLI completo, Storage, SMTP, realtime, hosting ni producción.

En este entorno el inicio del stack completo del CLI falló por espacio al descargar la imagen Supabase Postgres. Por eso se usa el harness mínimo documentado; las instrucciones estándar de Supabase local siguen en README. La primera prueba real detectó el nombre de variable del rol predeterminado de GoTrue; se corrigió contra su configuración pública, sin editar permisos de producto para pasar pruebas.
